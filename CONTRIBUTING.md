# Contributing

Thanks for helping improve the גינות העיר (Ginot HaIr) planning-watch site.
Everything in this repo is public - treat it that way.

## Ground rules

- **No personal data, ever.** Do not paste names, phone numbers, ID numbers,
  or permit "interested parties" fields (בעלי עניין / baaleiInyanList) into
  issues, PRs, code, or data files - even when the source data is public.
  The pipeline strips these fields on ingest; keep it that way.
- **No planner notes or statuses.** Internal committee tracking notes are
  never committed or published.
- **No secrets.** VPN credentials and tokens live in GitHub Actions secrets.
  Never print them; workflow logs use fixed categories, not raw daemon output.
- **Public sources only.** Data comes from public endpoints; no scraping
  behind logins, no CAPTCHA bypasses. If a source starts blocking, stop and
  open an issue instead of working around it.
- Analysis output aimed at the public site stays **DRAFT-labeled** and
  advisory; nothing is filed automatically with any authority.

## How work flows

1. **Open an issue first** (or comment on an existing one). Issue templates
  auto-apply `needs-triage`; bugs need evidence (run links, logs, data
  samples). See `docs/TRIAGE.md` for the label set, triage step, and
  milestone working-target convention.
2. **Small, focused PRs** referencing the issue (`fixes #N` / `refs #N`).
3. **Green CI required**: pytest matrix (3.10-3.13). Run `pytest` locally
  before pushing; `pip install -r requirements.txt` first.
4. **Squash merge** once checks pass. Commit messages explain the why and
   reference the issue.

## Project layout

- `src/ginot/` - site generation (`page.py`), diffing, selection logic.
- `scripts/` - data pipelines: `refresh.py` (weekly plans refresh),
  `mirror_ingest.py` (over.org.il permit mirror), `vpn/permit_feed.py` +
  `vpn/permit_enrich.py` (municipality permit feed over an owner-operated
  VPN), `vpn/l2tp.py` (tunnel management with sanitized logging).
- Permit enrich backfill scope (issue #99): the one-time publication-date
  backfill fetches only early/publication-stage tiks (~1,100 of 4,592 active
  ones). Skipped as late-stage: draft permit prepared, pink file / signed
  documents, deposit paid, approved by city engineer, shelved
  (`LATE_STAGE_STATUSES` in `vpn/permit_enrich.py`). Widen with the
  `include_late_stages=true` dispatch input / `--include-late-stages`.
- Starting a VPN run by code (issue #102): edit `data/backfill_request.json`
  (mode, include_unenriched, include_late_stages, limit, offset, new
  request_id) in a PR; when it lands on main the permit-feed workflow runs
  once with those values (same concurrency guard, no secrets in the file).
  The file is not cleared; a new run is a new edit. Backfill runs also write
  `data/permit_enrich_spotcheck.json` (step names and date presence for up to
  10 tiks that came back without publication dates).
- `.github/workflows/` - scheduled pipelines; see `docs/ARCHITECTURE.md`.
- `docs/` - the published GitHub Pages site (regenerated by the pipelines;
  do not hand-edit `docs/index.html` - change `src/ginot/page.py` and
  regenerate).

## Testing

```
pip install -r requirements.txt
python3 -m pytest -q
```

Page changes should add or update tests in `tests/test_page.py` and include
a regenerated `docs/index.html` in the PR so the change is live on merge.

## Diagrams

Anything that needs design (API, containers, architecture, data flow,
security boundaries, test pipeline) gets a diagram in the issue or in the
docs. Use Mermaid (fenced `mermaid` block): it renders on GitHub, is
version-controlled, and needs no binary files. Use generic example data
only: no real plates, locations or personal data. Check that it renders in
the preview before merging.

### Bug regression rule

Every `bug` issue must link an automated regression test in its fixing PR.
Name the test and explain the original failure it reproduces in the PR, then
link that evidence back from the issue before closing it. Prefer a browser
DOM/click test for interactive UI bugs, not a source-string assertion alone.
Run the regression and the full applicable suite before merge.

If an automated test is not feasible, the fixing PR must state why and link a
separate test issue with acceptance criteria. A manual check alone is not a
silent substitute. The bug issue must link that test issue too. See
[the recent-fix audit](tests/BUG_REGRESSIONS.md) for examples.

### Versions and release notes

Use semantic versions: Bug=PATCH, feature=MINOR, breaking=MAJOR. Update the
single package version, CHANGELOG and Hebrew/English notes together. See
[release process](releases/README.md). Use the standing release authority when CI is green; keep releases small and
frequent, without delaying deployment. Never include personal data in notes.

## Contributors: fork + PR, owner approval required

Fork the repo, work on a branch in your fork, and open a pull request. Nothing is merged into `main` without the owner's approval and green checks. Do not commit secrets or personal data (public repo).

## Issues: labels, milestones and order

The same scheme is used in every public repo. Do not add parallel label schemes.

**Labels** (every open issue has one type, one area and one priority)
- `type: feature | fix | task | docs | security` - the kind of work.
- `area: ...` - the part of the project (for example api, ci, containers, data, docs, quality, security). The list is per repo.
- `priority: high | medium | low` - high is done first.
- `status: blocked | held | in-progress | needs-review` - only when it applies. `status: in-progress` means someone claimed it.
- `needs-triage` - not sorted yet. Remove it when the three labels above are set.
- `good first issue` - small and clear, a good place to start.

**Milestones**
- `Now` - in progress or due this week. `Next` - planned after Now. `Later` - backlog.
- Every open issue is in exactly one. High priority goes to Now, medium to Next, low to Later, unless the maintainer decides otherwise. Repos may keep their own dated or goal milestones as well.

**How to pick an issue**
1. Open the repo's issues filtered by milestone `Now`, then `Next`.
2. Within a milestone, take `priority: high` first, then medium, then low. Prefer `good first issue` if you are new.
3. Skip anything with `status: blocked`, `status: held` or `status: in-progress`.
4. Comment "taking this" on the issue, then work from a fork and open a PR that references it.
